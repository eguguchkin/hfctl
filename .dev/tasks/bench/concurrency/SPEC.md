# SPEC сабстэджа: bench/concurrency

Дата 2026-11-14. Детализация продуктовой спеки (`../../SPEC.md` §13 контракты
роутов; бенч-команда — контракт этапа 2 «Э-2», PLAN.md) для сабстэджа
bench/concurrency. Противоречий продуктовой спеке не содержит; enum роутов
`bench_route` — константа артефакта `--compare` — НЕ меняется.

## 1 · Флаг `--parallel`

```
hfctl bench [quick|full] [--parallel N[,M…]] [существующие флаги]
```

- `--parallel` — список одновременности (целые 1..8, через запятую, без
  пробелов). Добавляет параллельный блок ПОВЕРХ выбранного режима:
  - `quick --parallel 2,4` = обычная quick-тройка + параллельные батчи 2 и 4;
  - `full` без флага = как сейчас (батчи 2 и 4);
  - `full --parallel 3` = full-сценарии, но параллельные батчи — из флага
    (флаг ЗАМЕНЯЕТ список, не дополняет).
- Порядок батчей — как перечислен пользователем. Дубли — не ошибка (меряется
  дважды).
- Каждый батч — ОДИН прогон (не умножается на `--runs`): нагрузка щадящая.
  Соло-сценарии перед параллельным блогом обязательны (они дают
  MED_SOLO_CODE — знаменатель процента масштабирования на lanes).
- Значение вне 1..8, не-целое, пустой список — `die` на разборе аргументов
  (до обращения к серверу), rc≠0, сообщение с полученным значением.

## 2 · Состав метрик параллельного блока (рамка D8 — только пол или готовые счётчики)

| Метрика | Источник (подпись в выводе) |
|---|---|
| per-request wall, по позиции запуска (порядок отправки = позиция в очереди FIFO) | секундомер curl на клиенте (уже есть: par_wall_$i) |
| aggregate tok/s | Σ usage.completion_tokens (пол ответа) / wall окна батча (date до/после) |
| wall окна батча | date до/после батча |

- В строке интерпретации и в примечании таблицы wall-числа подписаны
  «per-request wall (curl)»; aggregate — юнит `tok/s agg` (уже так).
- **Не выдумываем:** median TTFT по гистограмме `/metrics` в параллельном
  блоке НЕ измеряется — гистограмма движка суммарная по всему аптайму
  (FACTS.md: счётчики обновляются только в done; загрязнение чужим трафиком
  + интерполяция бакетов = мнимая точность). Это решение, а не отсрочка
  («Open questions» нет); live-скорости в процессе не существует.
- Разброс = min–max per-request wall (печатается в примечании).

## 3 · Семантика по роутам (уже реализовано — сохранить)

- `lanes` (flash-multi): строка «масштабирование: aggregate/solo = %.0f%%»;
  ровные по позиции per-request wall = параллельность реальна.
- `multi-slot`: очередь слотов (число слотов из /health — `bench_slots`).
- singleton/serial (27b-single, serial-fallback): «FIFO: aggregate ≈ solo —
  норма для serial-роута»; wall растёт по позиции — это ожидаемая картина,
  не дефект. Roут печатается в шапке bench (контракт §7/§13).

## 4 · Формат артефакта JSON (расширение с сохранением совместимости)

- `runs.tsv` строка `parallel-N` получает необязательную **колонку 7** —
  per-request wall'ы через запятую, в порядке запуска (секунды, %.1f),
  только для запросов с валидным usage; «-»/пусто — данных нет.
- `bench_report.py`:
  - `load_runs` кладёт колонку 7 в поле `walls` (массив float) записи
    `parallel-N`; старые строки без колонки 7 читаются как раньше;
  - любой ключ `parallel-<целое>` (в т.ч. 6/8/1, не только 2/4) участвует
    в report/summary/compare с юнитом `tok/s agg` (динамический порядок —
    после известных сценария ORDER, по возрастанию N);
  - `summary.parallel-N` — главная метрика aggregate tok/s (median/min/max),
    как сейчас для 2/4.
- **Совместимость `--compare` со СТАРЫМИ артефактами** (quick/full до сабстэджа):
  новая версия обязана сравнить с ними всё общее (соло-тройка, parallel-2/4,
  hol…) и корректно пропустить отсутствующее; ключ `walls` — additive:
  старые читатели его игнорируют, старый артефакт без него читается новой
  версией. Старый код + новый runs.tsv: колонку 7 парсеры не читают
  (столбцы 2..6), медианы не меняются.
- Пер-позиционный дельта-список wall'ов в --compare НЕ печатается
  (агрегат + соло-дельты дают сигнал регрессии; позиционная картина —
  живой вывод и JSON-артефакт).

## 5 · Прерывание и отказы (откат-безопасность)

- Ctrl-C в любой фазе: artifact пишется только после всех сценариев →
  оборванный прогон НЕ оставляет файла в `bench-runs/`; mktemp-каталог
  убирается существующим EXIT-trap'ом; rc 130/143 допустимы; сервер не
  страдает (запросы dying-клиента движок обрабатывает штатно).
- Сервер не отвечает / не готов / битый конфиг — существующие `die`
  (rc=1, внятное сообщение) — не регрессировать.
- Частичная неудача запросов батча: невалидные (curl/usage) исключаются и из
  суммы, и из `walls`; warn как сейчас; полное отсутствие usage — сценарий
  пропущен (не die).

## 6 · Бюджет нагрузки

- Фикстуры существующие (код — tpl/bench md5 `253c7ac5`, проза — ad-hoc
  c_prose), max_tokens 300 (как сейчас в bench_parallel); tpl/bench не трогать.
- quick+--parallel 2,4: ≈90 с соло + 2 батча; на FIFO-машине N=8×300 tok
  может занять до ~4 мин (per-request curl-таймаут 300 с) — это потолок
  флага, EXP'ы используют N≤4.
- Правок движка/конфига сервера нет (bench не меняет конфиг — контракт Э-2).
