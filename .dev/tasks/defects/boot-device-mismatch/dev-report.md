1. **GPU-ready wait перед первым up в `_boot`** (`lib/autostart.sh:4-53`):
   - константы вверху файла (:5–8): `GPU_WAIT_TIMEOUT=60`,
     `GPU_WAIT_INTERVAL=2` (как в брифе); пути гейта вынесены в глобалы
     `KFD_NODE`/`DRI_GLOB` с env-переопределением `HFCTL_KFD`/`HFCTL_DRI`
     — единственный способ фейкать девайсы в selfcheck без root
     (`/dev/dri` в песочнице нет), в проде не переопределяются;
   - `gpu_present()` (:22) — предикат «kfd И хотя бы одна renderD*»
     (та же логика, что была inline в цикле; card* намеренно не смотрит —
     у Halo card0 может не существовать);
   - `gpu_ready_or_die()` (:42–52) — цикл опроса до 60 с с шагом 2 с;
     по таймауту `die` с диагностикой: kfd есть/нет + вывод `ls /dev/dri`
     → rc 1, юнит перезапустит `_boot` сам (Restart=on-failure),
     причина остаётся в journal. Вызывается один раз в начале `cmd_boot`
     до цикла попыток.
2. **recreate-on-device-mismatch** (`hf_up_devsafe()`, :267–305):
   - **механика распознавания падения**: НЕ по rc compose — по паре
     «`podman inspect` статуса ≠ running **И** захваченный вывод
     `compose up -d 2>&1` содержит сигнатуру» — дословные подстроки
     `cannot stat` (crun) или `Failed to create container` (podman).
     rc заглушен (`|| true`): падение pull/сети сигнатуры не даёт и
     НЕ лечится — хелпер возвращает 1, дальше решает вызывающий;
   - лечение: `podman rm -f $(podman ps -aq --filter
     label=io.podman.compose.project=hipfire)` → повторный `compose up -d`
     — свежий create запечатывает актуальную нумерацию /dev/dri (это
     ровно ручное «stop → podman rm -f -a → start» из ребута evo, но
     точечно по лейблу проекта, не `-a` по всем контейнерам машины);
   - **число попыток: ровно ДВЕ попытки up на вызов хелпера** (первичный +
     один retry после rm; третий up хелпер не делает никогда). Вызов из
     `cmd_boot` — раз в ~10 с внутри его бюджета (дедлайн 420 с, потолок
     48 попыток не менялись); бюджет `_boot` ≤ ~10 мин (60 с wait + 420 с
     цикл + хвост ≤2–3 мин) < `TimeoutStartSec=900`;
   - lock прежний: `$STACK_DIR/.hfctl.lock`, flock -n (занято — «пропуск»,
     rc 0). Прежний ветвлённый механизм «`--force-recreate` со 2-й попытки
     под блокирующим flock -w 120» удалён целиком: сигнатурный rm
     срабатывает уже на первой итерации и не зависит от догадок «не
     поднялся → значит перенумерация».
3. **`_watchdog` — тот же класс защиты** (:376–403):
   - **выбранное поведение (зафиксировано по брифу)**: при неготовом GPU —
     быстрый single-check с отказом-тишины (`gpu_present || return 0`,
     без записи в лог): вотчдог минутный, он просто вернётся через минуту,
     а тик остаётся секундным — дословный 60-с wait сделал бы watchdog
     долгим. Порядок гейтов: маркер `.hfctl-stopped` проверяется ПЕРВЫМ
     (явная остановка уважается даже без GPU), GPU-гейт — вторым;
   - при контейнере ≠ running поднятие идёт через тот же `hf_up_devsafe`
     (`|| true`) — вотчдог больше не упирается в мёртвый контейнер с
     запечатанной старой нумерацией (раньше звал голый `hf_up_locked`).
     Формат лог-строки `.hfctl-watchdog.log` не менялся.
4. **Штатный путь без изменений** (п.3 решения брифа): up → running —
   ни rm, ни второго up; самоусловие проверено сценарием (а)/(ж) selfcheck.

## Known limitations / assumptions

- Две попытки up считаются НА вызов хелпера: `cmd_boot` зовёт его раз в
  ~10 с внутри своего бюджета, т.е. при устойчивом девайс-отказе rm+up
  повторится в каждой итерации цикла до дедлайна (~42 раза максимум) —
  но каждый цикл быстрый (create падает мгновенно на отсутствующей ноде)
  и во всём бюджете юнит-менеджер видит один запущенный `_boot`. Watchdog
  в аптайме при живом сервере этот код не трогает (контейнер running).
- `gpu_ready_or_die` различает только «ноды есть»/«нет за 60 с» — причин
  (amdgpu не загрузился / GPU сломан) не различает; диагностика в die
  (`ls /dev/dri`, kfd есть/нет) отдаёт разбор человеку.
- Ранний тик вотчдога при полупустом `/dev/dri` теперь молчит — защита
  от печати неполного device-снэпшота в свежий контейнер; цена — тик
  простоя (следующий через минуту), для минутного таймера несущественно.
- Сигнатурный grep работает по захваченному выводу `compose up -d`
  (2>&1); если podman-compose когда-нибудь начнёт печатать ошибку
  create только в системный journal, а не в stdout/stderr процесса —
  распознавание ослабнет до «не running без сигнатуры» (без лечения);
  известный сегодня вывод печатает обе подстроки в stderr процесса.
