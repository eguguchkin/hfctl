# План реализации спецификации hfctl (spec/hfctl.md)

Статус: принят 2026-11-08. Четыре этапа, каждый — отдельным коммитом (или
серией коммитов одного этапа) с приёмкой на тестовой 60 GiB-машине (этапы 1–3) или на
тестовой 128 GB-машине (этап 4) перед следующим.
Откат этапа = git revert до начала этапа.

Общие правила для всех этапов:
- живой прод на тестовой машине может быть остановлен только внутри приёмки этапа;
  после этапа сервер обязан стоять healthy на профиле `27b-single`;
- каждая смена конфига — recreate + wait_health + smoke (порядок фиксированный);
- найденные в догфуфе баги — правка + коммит в тот же этап, заметки в AGENTS;
- тесты идут по ssh-паттерну проекта (`ssh user@host 'bash -s' — ключ/адреса только в hflab, не здесь.`).

## Этап 1 — CLI-грамматика и профили (без flash)

### Что делается
1. В hfctl: таблица профилей (константы): `27b-single` (default),
   `27b-slots`. Для каждого: список тегов моделей, draft, конфиг-набор ключей
   (см. spec §5), ожидаемый режим в /health. Логика `_config_prod.sh`/`mode()`
   переезжает в таблицу.
2. Команды: `install [--profile P]`, `use <profile>`, `on`, `off`,
   `status [--json]`, `logs`, `uninstall`; скрытые алиасы `up|down|mode`.
   Команды `autostart/noautostart/`up/down` из help исчезают.
3. Канон профиля: `HFCTL_PROFILE` в `~/hipfire/.env`; boot-юнит (`_boot`)
   и вотчдог поднимают текущий канон, ничего не переопределяя.
4. Дефолт 27b-профиля: `HIPFIRE_MODEL=qwen3.8:27b-mq4-xts` (mq6-xt остаётся
   скачанной и доступной hot-swap'ом). При `install` поверх существующей —
   миграция старого `.env` без потери скачанного.
5. `status`: строка «профиль | автозапуск | health» + фактический режим
   движка из /health (`multi_slot`, модель); `--json` — машиночитаемо.

### DoD (все пункты зелёные на тестовой машине)
- [x] `use 27b-slots`: конфиг сменился, recreate, healthy, /health

- [x] `off`: контейнеры остановлены, юниты+таймер disabled, linger off; вотчдог
      НЕ воскрешает (70 c наблюдения); `on`: всё включается, healthy.

## Этап 6 — живая наблюдаемость: `hfctl watch`

Мотивация: движок hipfire НЕ логирует жизненный цикл запросов (проверка
по коду 0.4.5: в gateway только пер-запросные ошибки, `done`-событие
обрабатывается счётчиками молча; opt-in `HIPFIRE_LOG` instrumentation
пуст). На практике: «агент работает — в логах тишина, факт обработки
виден только по температуре GPU». Читаемая телеметрия уже существует
(`/stats`, `/metrics`), значит наблюдаемость поднимаем ВЕРХНЕУРОВНЕВО,
без касания движка (патч движка = путь апстрима/нового тега образа).

### Что делается

- `hfctl watch [--interval N]` (дефолт 2 c) в стиле однофайлового CLI:
  - статистика: `curl /stats` (`queue_depth`, `requests_served`,
    `recent_tok_s`, `retries_attempted`) + `curl /metrics`
    (`hipfire_cached_prompt_tokens_total`, `hipfire_requests_failed_total`);
  - строка печатается только на ИЗМЕНЕНИИ счётчиков; дельта `обслужено`
    и дельта `кэш` (tokens, реально отданные из сессийного кэша на
    последний запрос) на событии `done`;
  - температура GPU — всегда в строке: max °C по AMD-картам
    (`/sys/class/drm/card*/device/hwmon/temp1_input`, vendor `0x1002`);
  - в простое — heartbeat раз в ~60 c; недоступность — раз в ~30 c,
    восстановление без перезапуска (база сравнения сбрасывается —
    после поднятия свежая строка без ложных дельт);
  - `status` получает подсказку «живой наблюдатель запросов: hfctl watch».
- Патчи движка НЕ вносятся: инструментирование жизненного цикла запроса
  (request-start/TTFT/done-summary в stderr) остаётся темой отдельного
  апстрим-обсуждения (эффект — только с новым тегом образа).

### DoD (на тестовой машине)

- во время длинного запроса watch показывает `очередь: 1` на всём
  протяжении, после `done` — `обслужено +1` и правдоподобный `tok/s`
  (для mq4-xts ~130, для mq6-xt ~75 при серийном DFlash);
- в простое тишина (heartbeat ~60 c), Ctrl-C без артефактов; при генерации,
  длящейся >60 c без `done`, heartbeat формулируется как `обработка идёт
  (очередь: N…)`, а не «обменов нет»;
- температура GPU в watch совпадает с ручным `cat hwmon` и дышит
  в такт запросам;
- недоступность: стоп сервера → сообщения раз в ~30 c, старт → watch
  восстанавливается сам и печатает свежую строку;
- регресс-минимум: `status --json`, `logs -n 5`, цикл `off/on` зелёные.
