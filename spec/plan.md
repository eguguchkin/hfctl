# План реализации спецификации hfctl (spec/hfctl.md)

Статус: принят 2026-11-08. Три этапа, каждый — отдельным коммитом (или
серией коммитов одного этапа) с приёмкой на che-evo перед следующим.
Откат этапа = git revert до начала этапа.

Общие правила для всех этапов:
- живой прод на che-evo может быть выключен только внутри приёмки этапа;
  после этапа сервер обязан стоять healthy на профиле `27b-single`;
- каждая смена конфига — recreate + wait_health + smoke (порядок фиксированный);
- найденные в догфуфе баги — правка + коммит в тот же этап, заметки в AGENTS;
- тесты идут по ssh-паттерну hfbox (`ssh -i ~/.ssh/strix_halo_key … 'bash -s'`).

## Этап 1 — CLI-грамматика и профили (без flash)

### Что делается
1. В hfctl: таблица профилей (константы): `27b-single` (default),
   `27b-slots`. Для каждого: список тегов моделей, draft, конфиг-набор ключей
   (см. spec §5), ожидаемый режим в /health. Логика `_config_prod.sh`/`mode()`
   переезжает в таблицу.
2. Команды: `install [--profile P]`, `use <profile>`, `on`, `off`,
   `status [--json]`, `logs`, `uninstall`; скрытые алиасы `up|down|mode`.
   Команды `autostart/noautostart/`up/down` из help исчезают.
3. Канон профиля: `HFCTL_PROFILE` в `~/hipfire/.env`; boot-юнит (`_boot`)
   и вотчдог поднимают текущий канон, ничего не переопределяя.
4. Дефолт 27b-профиля: `HIPFIRE_MODEL=qwen3.8:27b-mq4-xts` (mq6-xt остаётся
   скачанной и доступной hot-swap'ом). При `install` поверх существующей —
   миграция старого `.env` без потери скачанного.
5. `status`: строка «профиль | автозапуск | health» + фактический режим
   движка из /health (`multi_slot`, модель); `--json` — машиночитаемо.

### DoD (все пункты зелёные на che-evo)
- [ ] `use 27b-slots`: конфиг сменился, recreate, healthy, /health
      `multi_slot: true`, smoke 200; `use 27b-single` обратно так же.
- [ ] `off`: контейнеры остановлены, юниты+таймер disabled, linger off; вотчдог
      НЕ воскрешает; `on`: всё включается, healthy.
- [ ] Повторный `install` (идемпотентность): ничего не докачивает, чинит
      канон, healthy.
- [ ] **Ребут-приёмка**: после переключения на `27b-slots` и ребута сервер
      загрузился на `27b-slots` без ручных команд; затем контрольный ребут
      на `27b-single`.
- [ ] `status` показывает профиль, режим и модель, соответствующие реально
      запущенному; `--json` парсится.
- [ ] Алиасы: `hfctl mode 27b-slots` == `use`, `up/down` работают, в help
      не видны.
- [ ] AGENTS.md обновлён (новая карта команд); git чистый.

## Этап 2 — гейты железа + профиль flash-multi

### Что делается
1. Общая функция префлайт-гейтов (зовётся из `install` и `use` до любых
   скачиваний/изменений): ОС, podman/podman-compose, /dev/kfd + renderD*,
   порт, gpu-lock (предупреждение), **RAM-гейт профиля** (порог — константа
   в шапке; для flash-multi 80 GiB, текстом с цифрами, spec §6).
2. Профиль `flash-multi`: таблица (модель `qwen3.8:flash-next-mq4-xts`,
   конфиг spec §5: vmm_batch=true + cbs=4 + multi_slot=false +
   dflash=off), ленивый pull split base + PLE sidecar (проверить, что
   init-контейнер тянет shared PLE по реестру и делает хардлинки).
3. Отображение фактического роута (spec §7): после `use`/`install` читать
   health/логи и печатать `lanes: vmm, cbs=4` ИЛИ `⚠️ qwen4 lanes refused:
   <причина> — fallback serial`; `status` включает поле батч-роута;
   `doctor` — доступность каждого профиля на этом железе.
4. `models`: список профилей с «доступен/нет (причина)» и размером докачки.

### DoD
- [ ] `use flash-multi` и `install --profile flash-multi` на che-evo (60 GiB):
      **отказ с текстом и цифрами до начала скачивания**, ничего не создано,
      код возврата ≠ 0, профиль не стал каноном.
- [ ] `doctor` печатает «flash-multi: недоступен (нужно ≥80 GiB, есть ~59.6)»,
      остальные профили — доступны.
- [ ] Гейты не ломают путь 27b: `install`/`use` на 27b-профилях проходят как
      на этапе 1 (регрессия: короткий цикл use↔use + off/on).
- [ ] Отказ префлайта в неинтерактивном режиме (без TTY) — тот же текст,
      без зависания на read.
- [ ] Конфиг-набор flash-multi проверяется на che-evo **только синтаксически**
      (config set не отклоняет ключи) — E2E отложен на 128 GB-машину
      (чекбокс в spec §12); в AGENTS записано, что проверено/не проверено.
- [ ] AGENTS.md обновлён; git чистый.

## Этап 3 — дистрибуция (путь новичка)

### Что делается
1. `install.sh` в корне репо: копирует `hfctl` в `~/.local/bin`, проверяет
   PATH (печатает готовую строку для rc-файла), печатает следующий шаг;
   поддерживает `curl … | bash`.
2. README.md: quickstart из 4 команд (clone → ./install.sh → hfctl install →
   curl-пример), таблицы «команда → что делает» и профилей, ссылки на
   spec/hfctl.md для деталей; минимальный раздел траблшутинга (hfctl doctor,
   перелогин/ребут после exit 42).
3. Финальный блок `install`: адрес `http://<IP>:<port>`, пример клиента
   (base_url + /v1/models), как сменить профиль/остановить/снести.
4. `--yes` для неинтерактива (вопросы только при TTY, цифры всё равно
   печатаются).
5. Публичный репозиторий (имя/org — из spec §12, решить до публикации).

### DoD
- [ ] На che-evo: `hfctl uninstall --purge-models --purge-image` → проверка
      «как будто никогда не было» (юниты, limits.d, контейнеры, volumes,
      сеть, образ, linger) — как уже обкатанный чеклист.
- [ ] Путь новичка целиком из чистого каталога (локальный clone этого репо):
      `./install.sh` → `hfctl install` → healthy + smoke; в PATH новый
      `hfctl`, `~/hipfire/` полной новой раскладки.
- [ ] Ребут после пути новичка: сервер поднялся сам, профиль канонический.
- [ ] `install.sh` идемпотентен (повтор = просто перезапись бинаря).
- [ ] README проганен глазами по букве: каждая команда из README выполнена в
      точном порядке и работает.
- [ ] AGENTS.md обновлён (hfctl-секция = новая грамматика); git чистый.

## Вне этапов (отложенное, не блокирует)

- E2E `flash-multi` на машине ≥ 128 GB (примут ли qwen4 fn-lanes gfx1151;
  калибровка порога RAM) — spec §12.
- Публикация на GitHub + `curl`-инструкция — после выбора org.
- `hfctl doctor --npu` (NPU-ветка) — вне объёма спецификации.
