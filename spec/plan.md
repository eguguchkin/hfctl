# План реализации спецификации hfctl (spec/hfctl.md)

Статус: принят 2026-11-08. Четыре этапа, каждый — отдельным коммитом (или
серией коммитов одного этапа) с приёмкой на che-evo (этапы 1–3) или на
che-max 128 GB (этап 4) перед следующим.
Откат этапа = git revert до начала этапа.

Общие правила для всех этапов:
- живой прод на che-evo может быть выключен только внутри приёмки этапа;
  после этапа сервер обязан стоять healthy на профиле `27b-single`;
- каждая смена конфига — recreate + wait_health + smoke (порядок фиксированный);
- найденные в догфуфе баги — правка + коммит в тот же этап, заметки в AGENTS;
- тесты идут по ssh-паттерну проекта (`ssh -i ~/.ssh/strix_halo_key … 'bash -s'`).

## Этап 1 — CLI-грамматика и профили (без flash)

### Что делается
1. В hfctl: таблица профилей (константы): `27b-single` (default),
   `27b-slots`. Для каждого: список тегов моделей, draft, конфиг-набор ключей
   (см. spec §5), ожидаемый режим в /health. Логика `_config_prod.sh`/`mode()`
   переезжает в таблицу.
2. Команды: `install [--profile P]`, `use <profile>`, `on`, `off`,
   `status [--json]`, `logs`, `uninstall`; скрытые алиасы `up|down|mode`.
   Команды `autostart/noautostart/`up/down` из help исчезают.
3. Канон профиля: `HFCTL_PROFILE` в `~/hipfire/.env`; boot-юнит (`_boot`)
   и вотчдог поднимают текущий канон, ничего не переопределяя.
4. Дефолт 27b-профиля: `HIPFIRE_MODEL=qwen3.8:27b-mq4-xts` (mq6-xt остаётся
   скачанной и доступной hot-swap'ом). При `install` поверх существующей —
   миграция старого `.env` без потери скачанного.
5. `status`: строка «профиль | автозапуск | health» + фактический режим
   движка из /health (`multi_slot`, модель); `--json` — машиночитаемо.

### DoD (все пункты зелёные на che-evo)
- [x] `use 27b-slots`: конфиг сменился, recreate, healthy, /health
      `multi_slot: true`, smoke 200; `use 27b-single` обратно так же.
      — live-прогоны 2026-11-08 (логи в сессии), health `режим: multi-slot/standard`
- [x] `off`: контейнеры остановлены, юниты+таймер disabled, linger off; вотчдог
      НЕ воскрешает (70 c наблюдения); `on`: всё включается, healthy.
- [x] Повторный `install` (идемпотентность): ничего не докачивает, чинит
      канон, healthy. + миграция v1-.env: модель сохраняется
      (искусственный v1-.env, mq6-xt остался дефолтом)
- [x] **Ребут-приёмка**: пройдена дважды — слоты→ребут→загрузился 27b-slots
      (`health ok multi-slot` через 15 c после UP); single→ребут→27b-single
      (`ok standard`). Ручных команд после boot ноль.
- [x] `status` показывает профиль, режим и модель, соответствующие реально
      запущенному; `--json` парсится. — слоты только в multi-slot; `--json`
      валиден json.tool'ом
- [x] Алиасы: `mode slots` == `use 27b-slots`, `down/up` работают; в help
      не светятся (grep = 0); `status --json` валиден (python3 json.tool);

## Этап 2 — гейты железа + профиль flash-multi

### Что делается
1. Общая функция префлайт-гейтов (зовётся из `install` и `use` до любых
   скачиваний/изменений): ОС, podman/podman-compose, /dev/kfd + renderD*,
   порт, gpu-lock (предупреждение), **RAM-гейт профиля** (порог — константа
   в шапке; для flash-multi 80 GiB, текстом с цифрами, spec §6).
2. Профиль `flash-multi`: таблица (модель `qwen3.8:flash-next-mq4-xts`,
   конфиг spec §5: vmm_batch=true + cbs=4 + multi_slot=false +
   dflash=off), ленивый pull split base + PLE sidecar (проверить, что
   init-контейнер тянет shared PLE по реестру и делает хардлинки).
3. Отображение фактического роута (spec §7): после `use`/`install` читать
   health/логи и печатать `lanes: vmm, cbs=4` ИЛИ `⚠️ qwen4 lanes refused:
   <причина> — fallback serial`; `status` включает поле батч-роута;
   `doctor` — доступность каждого профиля на этом железе.
4. `models`: список профилей с «доступен/нет (причина)» и размером докачки.

## Этап 3 — дистрибуция (путь новичка)

### Что делается
1. `install.sh` в корне репо: копирует `hfctl` в `~/.local/bin`, проверяет
   PATH (печатает готовую строку для rc-файла), печатает следующий шаг;
   поддерживает `curl … | bash`.
2. README.md: quickstart из 4 команд (clone → ./install.sh → hfctl install →
   curl-пример), таблицы «команда → что делает» и профилей, ссылки на
   spec/hfctl.md для деталей; минимальный раздел траблшутинга (hfctl doctor,
   перелогин/ребут после exit 42).
3. Финальный блок `install`: адрес `http://<IP>:<port>`, пример клиента
   (base_url + /v1/models), как сменить профиль/остановить/снести.
4. `--yes` для неинтерактива (вопросы только при TTY, цифры всё равно
   печатаются).
5. Публичный репозиторий (имя/org — из spec §12, решить до публикации).

## Этап 4 — живой тест flash-multi на второй машине (128 GB)

Хост: `hipfire@192.168.1.249` (тот же юзер, тот же ключ `strix_halo_key`),
железо с 128 GB пула. Модель GPU уточняется при первом подключении
(`lspci`, `free -g`, `hfctl doctor`) — от неё зависит, какие ожидания по
qwen4 fn-lanes вообще применимы (exact-роут документирован для gfx1201;
VMM QSA-стэйт Flash-Next заявлен «gfx1151/gfx1201 automatic»).

Может идти параллельно с этапом 3 (после этапа 2): на новой машине это
заодно первая боевая проверка «голой установки» (`bash hfctl install` или,
если этап 3 уже готов — путь новичка целиком).

### Что делается
0. **GO/NO-GO по памяти (ручное подтверждение пользователя):** перед любым
   действием на che-FAEX1 предупредить пользователя и дождаться, пока он
   остановит свой `gufo-qwen-flash` и подтвердит. Проверить фактически:
   `MemAvailable` ≥ ~100 GiB (gufo держит ~113 GB — пока он жив, этап не
   начинается ни на байт). Не останавливать gufo самостоятельно — это чужая
   рабочая нагрузка.
1. Разведка: ssh-доступ, ОС, GPU, размер пула, свободный диск ≥ ~90 GB
   (split base 70.9 GB + PLE q4 ~29 GB + образ).
2. Установка hfctl (с этой машины) → `hfctl install --profile flash-multi` —
   на 128 GB гейт должен пропустить.
3. Наблюдение принятия lanes: load-ack/health (`continuous_batch_route`,
   `continuous_batch_capable`) + лог (`qwen4 lanes refused: <причина>` vs
   принятие). Зафиксировать дословно в `.local-analysis/`.
4. Калибровка порога RAM: если admission/стабильность требуют больше 80 GiB
   — поправить константу в hfctl и spec §6/§5; если хватает — подтвердить.
5. Параллельный бенч: `scripts/conc_bench.sh` (или par_test) — N=2/4,
   измерить агрегат vmm-lanes vs solo (и vs fallback serial, если lanes
   отказали). Замеры — в `.local-analysis/`.
6. Если lanes отказали на этом GPU — зафиксировать причину и сделать
   `flash-multi` ожидаемо-serial профилем для данного роутера (UX-текст §7
   спецификации как раз для этого).
7. Ребут-приёмка flash-multi; затем (по желанию) `use 27b-*` для проверки
   обратного переключения на новой машине.
